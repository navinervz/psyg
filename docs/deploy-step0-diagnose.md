# قدم صفر — شناخت سرور قبل از دست زدن به آن

روی سرورت n8n در حال کار است. سایت می‌خواهد از همان پورت‌های ۸۰ و ۴۴۳
استفاده کند. اگر بدون بررسی جلو برویم، احتمال زیادی هست که n8n از کار
بیفتد و بعد باید هم سایت را راه بیندازی هم n8n را تعمیر کنی.

پس اول ببینیم آنجا چه خبر است.

---

## دستورها

به سرور SSH بزن:

```bash
ssh root@2.58.172.224
```

بعد این بلوک را **کامل** کپی کن و در ترمینال بچسبان:

```bash
echo "═══════ ۱. سیستم ═══════"
cat /etc/os-release | grep PRETTY_NAME
free -h | head -2
df -h / | tail -1

echo
echo "═══════ ۲. چه چیزی روی پورت ۸۰ و ۴۴۳ گوش می‌دهد ═══════"
ss -tlnp | grep -E ':(80|443|3000|5678)\s' || echo "  هیچ‌کدام"

echo
echo "═══════ ۳. Nginx نصب است؟ ═══════"
which nginx && nginx -v 2>&1 || echo "  نصب نیست"
ls /etc/nginx/sites-enabled/ 2>/dev/null || echo "  پوشه sites-enabled ندارد"

echo
echo "═══════ ۴. داکر و کانتینرها ═══════"
which docker >/dev/null 2>&1 && docker ps --format "  {{.Names}} | {{.Image}} | {{.Ports}}" || echo "  داکر نصب نیست"

echo
echo "═══════ ۵. گواهی SSL موجود ═══════"
ls /etc/letsencrypt/live/ 2>/dev/null || echo "  هیچ گواهی‌ای نیست"

echo
echo "═══════ ۶. پروکسی معکوس دیگر ═══════"
which caddy traefik apache2 2>/dev/null || echo "  چیز دیگری نیست"

echo
echo "═══════ ۷. فایروال ═══════"
ufw status 2>/dev/null | head -8 || echo "  ufw فعال نیست"
```

## خروجی را برایم بفرست

بر اساس آنچه ببینم، دقیقاً می‌گویم کدام مسیر را برویم. سه حالت ممکن است:

**حالت الف — n8n مستقیم روی پورت ۸۰ است، Nginx نیست.**
باید Nginx را جلوی هر دو بگذاریم. n8n به یک پورت داخلی منتقل می‌شود.
کمی کار دارد ولی نتیجه‌اش تمیزتر است.

**حالت ب — Nginx هست و n8n پشتش است.**
بهترین حالت. فقط یک فایل کانفیگ برای سایت اضافه می‌کنیم و n8n دست نمی‌خورد.

**حالت ج — چیز دیگری (Caddy، Traefik) جلوی n8n است.**
کانفیگ سایت را برای همان ابزار می‌نویسم؛ Nginx نصب نمی‌کنیم.

## در همین حین: دو کاری که الان می‌توانی انجام دهی

این دو کار به وضعیت سرور ربطی ندارند و n8n را هم تحت تأثیر نمی‌گذارند.

### ۱. رکوردهای DNS را اضافه کن

در کلادفلر، بخش **DNS** ← **Records** ← **Add record**:

| Type | Name | IPv4 address | Proxy status |
|---|---|---|---|
| A | `@` | `2.58.172.224` | **DNS only** (ابر خاکستری) |
| A | `www` | `2.58.172.224` | **DNS only** (ابر خاکستری) |

رکورد `n8n` را **دست نزن**. همان‌طور که هست (نارنجی) بماند.

> چرا خاکستری؟ چون برای گرفتن گواهی Let's Encrypt، سرور تایید باید
> مستقیم با سرور تو حرف بزند. اگر کلادفلر وسط باشد، تاییدیه به سرور تو
> نمی‌رسد و certbot با خطای «Timeout during connect» شکست می‌خورد.

### ۲. تنظیم SSL/TLS را فعلاً **دست نزن**

دیدم که روی **Flexible** است. می‌دانم قبلاً گفتم Full (strict) بگذار، ولی
با دیدن وضعیت واقعی‌ات نظرم عوض شد:

**تغییر این تنظیم الان n8n تو را از کار می‌اندازد.**

دلیلش: این تنظیم روی کل دامنه اعمال می‌شود، نه هر زیردامنه جدا. n8n الان
با Flexible کار می‌کند، یعنی کلادفلر با سرور تو روی HTTP ساده حرف می‌زند.
اگر Full (strict) بگذاری، کلادفلر از سرور گواهی معتبر می‌خواهد و اگر n8n
نداشته باشد، n8n می‌شکند.

**خبر خوب:** چون رکوردهای سایت را خاکستری می‌گذاریم، تنظیم SSL کلادفلر
اصلاً روی سایت اعمال نمی‌شود. سایت با گواهی واقعی Let's Encrypt و
HTTPS کامل بالا می‌آید، و n8n هم دست‌نخورده می‌ماند.

بعداً که همه‌چیز پایدار شد، اگر خواستی مزایای پروکسی کلادفلر (پنهان شدن
IP، محافظت در برابر حمله) را داشته باشی، آن موقع n8n را هم درست می‌کنیم
و با هم به Full (strict) می‌رویم.

---

## ⚠️ یک هشدار مهم

**تا وقتی SSL روی Flexible است، رکورد سایت را نارنجی نکن.**

کانفیگ Nginx ما پورت ۸۰ را به HTTPS ریدایرکت می‌کند. ترکیب
«Flexible + ریدایرکت اجباری HTTPS» یعنی حلقه‌ی بی‌نهایت ریدایرکت و سایت
اصلاً باز نمی‌شود. همان هشداری که خود کلادفلر در تصویر داده:

> Will cause errors if your origin forces HTTPS.
