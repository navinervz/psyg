# اتصال هوش مصنوعی به سایت (MCP)

سایت یک اندپوینت MCP دارد که با آن می‌توانی من — یا هر دستیار دیگری که
MCP را پشتیبانی کند — را مستقیم به سایت زنده‌ات وصل کنی.

---

## اول یک حرف صریح درباره‌ی امنیت

خواسته‌ی تو این بود: «دسترسی به همه چیز داشته باشی و هر کاری خواستم انجام
بدی.» من عمداً این کار را نکردم و دلیلش را باید بدانی.

اندپوینتی که بتواند فایل عوض کند یا دستور اجرا کند، **یک در پشتی روی سرور
پروداکشن است**. توکن آن دیر یا زود از یکی از این راه‌ها بیرون می‌رود:
تاریخچه‌ی یک چت، اسکرین‌شات، لاگ یک سرویس واسط، یا یک لپ‌تاپ گم‌شده. از آن
لحظه هرکس آن را دارد می‌تواند سایتت را عوض کند، لینک‌های افیلیت را به نام
خودش بزند، یا بدافزار روی صفحاتت بگذارد — و تو هفته‌ها متوجه نشوی.

**پس این MCP فقط-خواندنی است.** به من دید می‌دهد، نه دست.

این محدودیت چیزی از کارایی کم نمی‌کند، چون تغییرات واقعی باید از مسیر امن
انجام شوند: من کد را اینجا عوض می‌کنم، تست می‌گیرم، تو `git pull` و
`docker compose up -d --build` می‌زنی. همان مسیری که تا حالا رفته‌ایم و
هر تغییرش قابل بازگشت و قابل بازبینی است.

اگر روزی واقعاً به عملیات نوشتنی نیاز شد، راه درستش این است: عملیات مشخص و
محدود (نه دستور دلخواه)، روی یک محیط جدا، با تایید دستی تو برای هر تغییر.

---

## چه چیزی به من می‌دهد

| ابزار | کارش چیست |
|---|---|
| `site_status` | تعداد محصولات و مقالات، فروشگاه‌های فعال، و اینکه کدام تنظیمات پر شده‌اند |
| `list_products` | فهرست محصولات با فیلتر دسته و مرتب‌سازی |
| `get_product` | جزئیات کامل یک محصول با تاریخچه‌ی ۳۰ روزه و تحلیل خرید |
| `search_products` | جستجو در عنوان و برند |
| `price_analysis` | بیشترین افت و افزایش، وضعیت هر دسته، محصولات نزدیک کف قیمت |
| `list_categories` | دسته‌ها با تعداد محصول |
| `list_articles` | فهرست یا متن کامل مقالات مجله |
| `homepage_content` | آنچه همین الان روی صفحه‌ی اصلی است |
| `security_audit` | **بررسی خودکار امنیت سایت** |

### `security_audit` مهم‌ترینشان است

این ابزار سایت زنده را بررسی می‌کند و می‌گوید کجا ضعف دارد:

- هدرهای امنیتی HTTP وجود دارند یا نه
- `robots.txt` مسیرهای حساس را بسته یا نه
- توکن MCP به‌اندازه‌ی کافی قوی است یا نه
- آیا متغیر محرمانه‌ای اشتباهاً در سمت مرورگر افشا شده
- لینک‌های افیلیت امن‌اند یا نه

هر یافته سه چیز دارد: **چه چیزی غلط است، چرا مهم است، چطور درست می‌شود.**
توصیه‌ی بدون «چرا» یا نادیده گرفته می‌شود یا کورکورانه اجرا — هر دو بد است.

بعد از دیپلوی، اولین کاری که با MCP می‌کنیم همین است.

## راه‌اندازی

### ۱. توکن بساز

روی سرور:

```bash
openssl rand -hex 32
```

خروجی یک رشته‌ی ۶۴ کاراکتری است. آن را در `.env` بگذار:

```
PSYG_MCP_TOKEN=<همان رشته>
```

سپس:

```bash
docker compose up -d
```

> توکن سمت سرور خوانده می‌شود، پس نیازی به `--build` نیست.

### ۲. تست کن که کار می‌کند

```bash
curl -s https://psygstore.shop/api/mcp \
  -H "Authorization: Bearer $PSYG_MCP_TOKEN"
```

باید فهرست ابزارها را برگرداند. بدون هدر باید ۴۰۱ بدهد:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://psygstore.shop/api/mcp
# انتظار: 401
```

### ۳. به کلاد وصل کن

فرم «Add custom connector» در کلاد فقط یک URL می‌گیرد و امکان تنظیم هدر
`Authorization` ندارد (فقط OAuth را پشتیبانی می‌کند). برای همین اندپوینت
یک مسیر دوم دارد که توکن را از خود آدرس می‌خواند.

در claude.ai برو به **Settings** ← **Connectors** ← **Add custom connector**:

| فیلد | مقدار |
|---|---|
| Name | `PsyG` |
| URL | `https://psygstore.shop/api/mcp/<TOKEN>` |
| OAuth Client ID | خالی بگذار |
| OAuth Client Secret | خالی بگذار |

به‌جای `<TOKEN>` همان رشته‌ی ۶۴ کاراکتری را بگذار. یعنی آدرس نهایی چیزی
شبیه این می‌شود:

```
https://psygstore.shop/api/mcp/0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
```

> عدد بالا عمداً یک نمونه‌ی آشکارا ساختگی است. نسخه‌ی قبلی این سند شش
> کاراکتر اول توکن واقعی را نشان می‌داد — نشتی کامل نبود، ولی وقتی این
> مخزن عمومی شود حتی همان مقدار هم بی‌دلیل است.

از آن به بعد می‌توانی بگویی «وضعیت سایتم را بررسی کن» یا «ممیزی امنیتی
بگیر» و من مستقیم از سایت زنده می‌خوانم.

### دو مسیر، یک منطق

| مسیر | احراز هویت | چه زمانی |
|---|---|---|
| `/api/mcp` | هدر `Authorization: Bearer` | هر کلاینتی که هدر می‌پذیرد |
| `/api/mcp/<token>` | توکن در آدرس | کلاینت‌هایی که فقط URL می‌گیرند |

هر دو دقیقاً همان کد و همان سخت‌گیری را دارند — تست‌ها بررسی می‌کنند که
رفتارشان یکسان باشد.

**تفاوت امنیتی:** توکن در URL ممکن است در لاگ سرویس‌های واسط (مثلاً
کلادفلر) ثبت شود، در حالی که هدر معمولاً لاگ نمی‌شود. این مصالحه آگاهانه
است چون همه‌ی ابزارها فقط-خواندنی‌اند و بدترین حالت این است که کسی
داده‌ی عمومی محصولات را ببیند. اگر کلاینتت هدر می‌پذیرد، از مسیر اول
استفاده کن.

## اگر توکن لو رفت

```bash
# توکن جدید
openssl rand -hex 32

# در .env جایگزین کن، بعد
docker compose up -d
```

توکن قدیمی بلافاصله بی‌اثر می‌شود. لازم نیست کار دیگری بکنی — چون هیچ
عملیات نوشتنی وجود نداشته، حداکثر ضرر این است که کسی داده‌ی عمومی سایتت
را دیده باشد.

## جزئیات فنی

- پروتکل: MCP نسخه‌ی `2025-06-18` روی JSON-RPC 2.0
- ترنسپورت: HTTP با متد POST
- بدون وابستگی خارجی — پیاده‌سازی مستقیم در `src/lib/mcp/`
- سقف حجم درخواست: ۶۴ کیلوبایت
- هیچ پاسخی کش نمی‌شود
- محدودیت نرخ: ۱۰ درخواست در دقیقه (از سمت Nginx روی `/api/`)

### چرا SDK رسمی استفاده نشده؟

سه دلیل: وابستگی کمتر یعنی سطح حمله کمتر (این اندپوینت روی اینترنت باز
است)، کل چیزی که لازم داریم چهار متد است، و کد بدون وابستگی را می‌شود
کامل تست کرد. ۳۱ تست واحد فقط برای همین بخش نوشته شده.

### چه چیزی هرگز برنمی‌گردد

- ایمیل مشترکین خبرنامه
- مقدار هیچ متغیر محیطی (فقط «ست شده یا نه»)
- محتوای فایل‌های سرور
- جزئیات خطاهای داخلی (در لاگ سرور می‌ماند)
